# 깨움 (KKAEUM)

라벨과 실질이 다른 퇴직연금 디폴트옵션을 진단하는 서비스.

2026 금융 AI Challenge 출품 준비 저장소.

---

## 문제

디폴트옵션 적립금의 84.5%(47.2조 원)가 초저위험 상품에 몰려 있다
(324개 상품·41개 사업자 비교공시 2026년 1분기 기준, `data/providers.json`로 검증 가능).
제도는 있지만 가입자는 자기 연금이 무엇을 하고 있는지 모른다.

더 근본적인 문제는 **라벨이 실질을 가린다**는 점이다.
포트폴리오 위험등급은 구성상품 등급의 가중평균으로 산출되므로,
자산의 절반이 고위험 상품이어도 평균값 때문에 '저위험'으로 표시될 수 있다.

실측 결과 (사업자 6곳·포트폴리오 15개 표본, `python scripts/03_verify_engine.py`로 재현 가능):

| 라벨 | 위험자산 비중 범위 | 격차 |
|---|---|---|
| 저위험 | 40% ~ 60% | 20%p |
| 중위험 | 60% ~ 100% | 40%p |
| 고위험 | 80% ~ 100% | 20%p |

그리고 **라벨 구간이 서로 겹친다.**
'저위험' 상단(60%)과 '중위험' 하단(60%)이 같고,
'중위험' 상단(100%)과 '고위험' 하단(80%)도 겹친다.

→ 한 등급 낮은 라벨을 고른 가입자가 다른 사업자의 한 등급 높은 라벨과
  동일한, 혹은 더 큰 위험을 지고 있다.

별도로 324개 상품 전체를 라벨별 **1년 수익률**로 비교하면 격차는 더 크다
(예: '중위험' 라벨 87개 상품의 1년 수익률이 3.97%~22.55%로 18.58%p 벌어짐,
`python scripts/04_build_dataset.py`로 재현 가능) — 이건 위 표(구성상품
위험자산 비중)와는 다른 축의 근거이며, 둘 다 기획서 §1.2에 정리돼 있다.

## 설계 원칙

### 숫자는 코드가, 말은 AI가

```
LLM 담당   문서 정규화 · 근거 기반 설명 · 개인 맥락 해석
코드 담당   가중평균 · 복리 계산 · 격차 산출
```

금융 서비스에서 LLM이 산수를 하면 환각이 금액 오류로 직결된다.
`lib/` 아래 계산 모듈에는 LLM이 개입하지 않는다.

### 외부 런타임 의존 0

공시 데이터를 런타임에 호출하지 않는다. 사전 수집·검증한 정적 JSON을
저장소에 동봉해 배포한다. 심사 기간 중 외부 사이트 장애가
서비스 다운으로 이어지지 않게 하기 위함.

### 추천하지 않는다

특정 사업자나 상품을 권하지 않는다. 산출물은 "당신의 위치는 여기입니다"까지다.
판단은 사용자가 한다.

이는 규제 회피이자 설계 철학이다. "옮기세요"는 반박당하지만
"당신 위치는 여기입니다"는 반박할 수 없다.

## 실행

### 앱 (Next.js)

```bash
npm install
npm run dev
```

`http://localhost:3000/diagnose`에서 기본정보를 입력하면 `/chat`으로 넘어간다.

**화면 흐름**

```
/            랜딩
  ↓
/diagnose    ① 기본정보 입력 (나이·은퇴나이·적립금·납입액·사업자·위험등급)
  ↓            입력값을 sessionStorage에 저장
/chat        ② 챗봇 — 저장된 정보를 읽어 컨텍스트로 사용
               '정보 수정'으로 ①로 되돌아가면 입력값이 복원된다
```

**반응형 레이아웃**

모바일 우선으로 설계하되 큰 화면에서는 넓혀 쓴다. 제출물이 배포 URL이라
심사가 데스크톱에서 이뤄질 가능성이 높다.

| 화면 | 랜딩·입력 | 챗봇 |
|---|---|---|
| 모바일 (<1024px) | 430px 단일 단 | 단일 단, 근거는 인용 아래 인라인 |
| 데스크톱 (≥1024px) | 560px (폼은 넓다고 좋지 않다) | **2단** — 왼쪽 대화, 오른쪽 원문 근거(sticky) |

챗봇 2단이 중요한 이유: 답변과 상품설명서 원문을 나란히 놓고 대조할 수 있어야
'근거 투명성'이라는 주장이 말이 아니라 화면으로 증명된다. 1280px 기준
화면 사용률 34% → 92%, 원문 이미지 폭 282px → 516px.

근거 선택 상태(`openEvidence`)는 `ChatPanel`이 들고 있고 두 레이아웃이
공유한다. 상태를 각자 두면 화면 폭이 바뀔 때 서로 어긋난다.

입력값은 **서버로 저장되지 않는다.** sessionStorage에만 두므로 탭을 닫으면
사라진다(기획서 §4.4의 "세션 종료 시 소멸"). URL 쿼리스트링을 쓰지 않는
이유는 나이·적립금이 주소창·히스토리·리퍼러에 남기 때문이고, localStorage를
쓰지 않는 이유는 탭을 닫아도 남아 공용 PC 사용자에게 위험하기 때문이다.

`/chat`에 정보 없이 직접 들어오면 입력 화면으로 안내한다 — 진단 컨텍스트가
없으면 이 챗봇은 일반 문서 챗봇과 다를 바 없어지기 때문이다.

입력 검증 규칙은 `lib/profile.ts`의 `validateProfile()` 하나뿐이며 폼과 API
라우트가 함께 쓴다. 규칙이 갈라지면 폼은 통과시키는데 API가 거부하는 상태가 생긴다.

**API 키 없이도 전부 동작한다.** 키가 없으면 검색·계산·인용만으로 답변을
구성하는 "근거 기반 요약 모드"로 떨어지고, 화면에 그 사실을 표시한다.
AI 서술을 켜려면 저장소 루트에 `.env.local`을 만든다:

```bash
cp .env.example .env.local
```

`.env.local`의 `ANTHROPIC_API_KEY=` 뒤에 키를 채워 넣으면 된다.
**Next.js 앱과 Python 스크립트가 이 파일 하나를 공유한다** —
Next는 자체적으로 읽고, Python은 `scripts/_env.py`가 읽는다.

| 항목 | 내용 |
|---|---|
| 우선순위 | `export`한 환경변수 > `.env.local` > `.env` |
| 커밋 여부 | `.env*`는 전부 gitignore. `.env.example`만 저장소에 남는다 |
| 노출 범위 | **서버 전용.** `app/api/ask`에서만 읽고 브라우저로 가지 않는다 |
| 키가 틀리면 | 오류로 죽지 않고 요약 모드로 강등된다(`degraded: true`) |

`NEXT_PUBLIC_` 접두사는 절대 붙이지 말 것 — Next.js가 그 접두사가 붙은
환경변수를 클라이언트 번들에 그대로 인라인해 누구나 볼 수 있게 된다.

Vercel 배포 시에는 `.env.local`이 아니라
**Project Settings → Environment Variables**에 등록한다.

테스트:

```bash
npm test
```

## 챗봇(M4)이 동작하는 방식

기능명세서 §3의 M4를 구현한 것으로, 일반 문서 챗봇과 다른 점은
**사용자 진단 결과와 계산 엔진 출력이 함께 입력으로 들어간다**는 것이다.

```
질문 + 진단 입력
   ↓
① 계산 엔진    riskEngine + simulate + products.json 분포   ← LLM 미개입
   ↓          → 확정 숫자 (가중평균, 위험자산%, 라벨 내 분포, 등급별 예상액)
② 문서 검색    chunks.json 대상 BM25 (원문 3개 자리 예약)    ← LLM 미개입
   ↓
③ 근거 게이트  relevance < 0.06 이면 여기서 답변 거부        ← LLM 호출 안 함
   ↓
④ 답변 생성    키 없음 → 템플릿 폴백 / 키 있음 → Claude 서술
   ↓
⑤ 숫자 검증    계산 엔진·문서에 없는 숫자가 있으면 경고 표시
   ↓
⑥ 등급 판정    원문을 인용했는가 → documented / no_document
   ↓
⑦ 근거 표시    documented면 원문 PDF 페이지에 형광펜 마킹
```

### 답변 등급 3단계

| 등급 | 뜻 | 화면 |
|---|---|---|
| `unrelated` | 서비스 범위 밖 | 답변 거부. LLM 호출도 안 함 |
| `no_document` | 관련은 있으나 공식 문서에 근거 없음 | 계산 결과로만 답변. **문서 인용 안 붙임** |
| `documented` | 공식 문서 원문에 근거 있음 | 인용 + 원문 페이지 형광펜 마킹 |

**relevance로 3단계를 나누지 않는다.** ①과 나머지를 가르는 데는 relevance가
잘 듣지만(무관 0.000~0.025 vs 관련 0.038~), ②와 ③은 나눌 수 없다 —
실측 결과 두 무리가 겹친다(문서 밖 최대 0.228 > 문서 안 최소 0.118).
relevance는 '어휘가 겹치는가'를 재지 '문서가 답을 담고 있는가'를 재지 않기
때문이다. 예: '물가'는 문서에 나오지만("수익률이 물가상승률보다 낮을 수
있으며") "물가 오르면 어떻게 되나요"에 답하지는 않는다.

→ ②와 ③은 **답변이 실제로 원문을 인용했는지**로 판정한다. 정의상 정확하다.
LLM 경로는 모델이 고른 `citedChunkIds`로, 폴백 경로는 원문 문장과 질문의
bigram 커버리지(≥0.3)로 정한다.

**②에 문서 인용을 붙이지 않는 이유**: 약하게 걸린 문단을 '근거'로 보여주면
문서가 그 답을 뒷받침한다는 오해를 준다. 근거 투명성을 내세우는 서비스에서
이건 손해다.

**설계상 지킨 것**

- 거부를 코드가 결정한다. 프롬프트에 "근거 없으면 거부하라"를 맡기면
  모델이 어길 수 있으므로, BM25 상대 점수가 임계값 미만이면 LLM을
  호출조차 하지 않는다.
- 금액·비율은 `lib/calcFacts.ts`만 만든다. LLM은 그 숫자를 서술만 한다.
  응답에 출처 불명 숫자가 있으면 `validateNumbers()`가 화면에 경고를 띄운다.
- 폴백과 LLM 경로의 반환 구조가 같아서 UI가 분기하지 않는다.
- 벡터DB·임베딩을 쓰지 않는다(청크 377개 규모에서 인프라 추가 비용 대비
  이득이 없고, 임베딩 API는 "외부 런타임 의존 0" 원칙과 충돌).
- **원문 청크 자리를 3개 예약한다**(`minOriginalText`). 구성내역 정규화본은
  15개뿐인데 짧고 밀도가 높아 BM25 상위를 독점한다 — 실측상 "원금 손실이
  발생할 수 있나요"의 1~4위가 전부 정규화본이었다. 페이지 좌표는 원문에만
  있으므로, 예약하지 않으면 documented 등급이 나올 수 없다.
- 형태소 분석기 없이 한국어를 다룬다. 어절 전체 + 문자 bigram을 함께
  색인해 조사 변형("수익률/수익률은/수익률이")을 흡수한다. 한 글자 어절은
  색인하지 않는다 — 조사·어미 조각이거나 PDF 줄바꿈 파편인데 희귀해서
  IDF만 최대로 받아 순위를 뒤집기 때문이다.
- 인용한 구절을 **원문 PDF 페이지 위에 형광펜으로 표시**한다. 사용자가
  "정말 그렇게 쓰여 있나"를 그 자리에서 확인할 수 있다. 런타임에 PDF를
  다루지 않고 빌드 타임에 구운 이미지 + 정규화 좌표만 쓰므로 의존성이 0이다
  (PDF.js 미사용). 스캔 PDF인 미래에셋증권은 좌표를 만들 수 없어 미지원.
- 근거가 약하면 거부 대신 **한계를 밝히고 답한다**. 문서 관련도가
  `LOW_CONFIDENCE_RELEVANCE`(0.15) 미만이면 "질문하신 내용이 문서에 직접
  나와 있지 않을 수 있습니다"를 덧붙인다. 은퇴 예상액처럼 답이 문서가 아니라
  계산 엔진에 있는 질문을, 문서 근거가 없다는 이유로 묵살하지 않기 위해서다.
